# Claims

One file per claim under `claims/<type-plural>/`, each with `id:` and `about:`.

* [A test of a start-time refusal that awaits the exit hangs, not fails, on code without the refusal](lessons/a-refusal-test-that-awaits-the-exit-hangs-on-code-without-the-refusal.md) - A test that asserts a process refuses at start by awaiting its exit never settles on code that lacks the refusal, because that code starts its children and runs; give the test its own timeout, and prove 'fails on the old code' under a timeout, checking for fixture processes left behind.
* [Claude Code's sandbox widens by exact entries across settings sources, with four traps for an agent's own tools](lessons/claude-codes-sandbox-widens-by-exact-entries-but-has-four-traps.md) - In bb's sandboxed modes Claude Code's sandbox allowances add up across settings sources, so a home's settings.local.json can widen a launcher's sandbox by exactly one host or path; but an allowWrite on a missing directory can't create it, git reaches the network only through proxy settings carried in GIT_* variables, a listed host resolving to the machine itself is refused, and aw reaches its registry through the host the service's discovery names.
* [Claude Code applies a home's .claude/settings.local.json env inside a bb thread, so launch env need not pass through bb](lessons/claude-code-applies-a-homes-settings-local-env-inside-a-bb-thread.md) - With bb's own machine and project env empty, a Claude Code thread bb starts in an OATS home applies the env block of the home's settings.local.json to its process, its Bash tool and its hooks; so a launcher can keep launch env in the 0700 home rather than in bb's unauthenticated database, as long as the thread's cwd is the home and no secret goes in the file.
* [A bb thread has no "stopped" status, so a session backend over bb records its own stop](lessons/a-bb-thread-has-no-stopped-status-so-a-session-backend-records-its-own-stop.md) - bb's thread statuses are pending, idle, starting, active, stopping and error; a settled stop reads idle and any tell restarts the thread, so a kernel that runs agents as bb threads must record its own stop and refuse input to a home it stopped, or a mail silently restarts a stopped agent.
* [The bb switch in the team image's supervisor is an interim: the end state is a generic optional child, with bb's image and relay in bb's own repository](decisions/the-bb-switch-in-the-team-image-supervisor-is-an-interim.md) - Pepe's side accepted the bb-specific supervisor switch, derived image and relay in the oats repository only as an experimental interim with no compatibility promise; the end state is a base supervisor that knows nothing of bb and runs a generic optional child a derived image declares, with the bb image, its pin and the relay beside the bb provider.
* [A supervisor that restarts a launcher must own its process group, or a killed launcher's children hold the ports](lessons/a-supervisor-that-restarts-a-launcher-owns-its-process-group.md) - In the team image, killing bb's launcher with SIGKILL left its server and host daemon alive on their ports, reparented to the init process, so every restart failed; spawning the launcher as a process-group leader and killing what is left of the group before a restart made the restart work.
* [A third-party server joins the team container by a derived image, with its switch in the base supervisor](decisions/a-third-party-server-joins-the-team-container-by-a-derived-image.md) - The team image stays the image every team trusts: an optional third-party server (bb the first) ships in a derived image built from it, turned on by one fixed switch the base supervisor refuses without the binary, stays on loopback, and does not take the agents down when it fails.
* [A loopback service in a team container is reachable over SSH command channels, so allowing a port forward is convenience, not a boundary](lessons/a-loopback-service-is-reachable-over-ssh-command-channels.md) - With sshd's forwarding disabled, one SSH command channel per connection (stdio piped to the loopback port, multiplexed on a ControlMaster) carried a web app and its WebSockets for ten minutes with no drop; a forward limited by PermitOpen also works and refuses every other target, but the same key reaches those targets through a command channel either way.
* [bb accepts loopback and IP hosts as they are, and a DNS name only through BB_APP_URL set in the server's own data dir](lessons/bb-accepts-a-dns-name-only-through-bb-app-url-in-its-own-data-dir.md) - bb-app 0.50.1 answers 403 to every request under a DNS name that is not in BB_APP_URL, while a loopback listener on any port needs no setting; bb-app config set writes the default data dir and still reports a reload, so with a server started on --data-dir it must run with BB_DATA_DIR set to that dir.
* [bb thread tell answers "sent" in a Claude thread's ordinary states, and its "queued" for a starting turn drains by itself](lessons/bb-tell-answers-sent-in-ordinary-states-and-queued-drains-itself.md) - In bb-app 0.50.1 a `bb thread tell --mode auto` into a Claude Code thread answers delivery "sent" when the thread is idle (with or without a live Claude process), mid tool call and in error; it answers "queued" with waitingOn turn-starting only in the short window while another tell restarts the thread, and bb delivers that message unaided within about a second. Each message reached the model once.
* [A bb restart holds wake-broker mail cleanly but strands a wake already steered into a turn](lessons/a-bb-restart-holds-broker-mail-but-strands-a-steered-wake.md) - With the aw wake broker delivering into a bb thread through bb thread tell, mail sent while bb is down arrives exactly once after it returns, provided session inspect fails while bb is unreachable; but bb never resumes an interrupted turn, and a wake bb had already accepted as a steer leaves the thread in status error, acknowledged and without a turn, until a later tell restarts it.
* [Pinned instances lead their machine's list, from a pin the kernel keeps in the home](decisions/pinned-instances-lead-their-machine-list.md) - A pin is a home fact every client reads (`oats instance pin on|off`, row `pinned: true`, feature instance-pin), shared by everyone who views that machine; the shared roster order puts a node whose subtree holds a pin first at every level, ahead of spawn time.
* [The kernel's presentation verbs refuse only beside a retire, so a spec that mirrors one states exactly that](lessons/presentation-verbs-refuse-only-beside-a-retire.md) - `instance color`, `background`, `same-work` and `pin` share refuseBesideRetire, which never blocks a live stop, start or upgrade; a spec that promises E_LIFECYCLE_BUSY for "a concurrent lifecycle act" contradicts the verb it copies and stops the build.
* [Sidebar roots start collapsed behind a disclosure before the name, and a row its lifecycle takes stays open](decisions/sidebar-roots-start-collapsed-lifecycle-rows-stay-open.md) - In the Desktop sidebar a row with children wears a chevron and the count of every row under it, first on its name line; each section root with children starts collapsed in every window and nested parents start open; a row drawn as a pending spawn or a held home is always drawn open with no disclosure, because its state leaves no room for the needs-input roll-up.
* [In a bb Claude thread a permission prompt becomes oats.core's claim, and a bb tell waits behind it](lessons/a-bb-permission-prompt-is-an-oats-claim-and-a-tell-waits-behind-it.md) - With the OATS env set for a bb Claude Code thread, a Bash permission interaction still fires Claude's own hooks, so oats.core records a permission claim in the home's events; but session inspect reads such a home as not launched, a spawn-only home lacks the PermissionRequest hook, and a bb tell sent meanwhile neither answers nor cancels the interaction but queues until it is resolved.
* [The aweb-channel plugin takes mail in a Claude session started without --channels, and no turn sees it](lessons/aweb-channel-plugin-consumes-mail-without-the-channels-flag.md) - Enabled at user scope, the plugin's MCP server starts in every Claude session that loads plugin MCP servers, flag or not; without `--channels plugin:aweb-channel@...` Claude injects nothing, yet the identity's mail is marked read. Any non-OATS start of Claude in an OATS home passes the flag or keeps the plugin off.
* [aw's non-acking mail read is mail threads plus mail show; the local interaction log is not a mail record](lessons/aw-non-acking-mail-read-is-threads-and-show.md) - To observe an identity's mail, received and sent, without acknowledging it, use `aw mail threads` (aw 1.36.53+) and `aw mail show`, both server reads that ack nothing; `aw mail inbox` acks what it shows even with --show-all, and aw's local communication and interaction logs record received mail only when an acking aw verb (`aw mail inbox`, or a beads-mail or gc-mail read) presented it on that machine, so mail a channel delivers without them never appears there.
* [A case a recorded decision leaves open blocks the PR at the green light; settle it before the build](lessons/a-case-a-decision-leaves-open-blocks-at-the-green-light.md) - When a change follows a decision that names a case it does not decide, and the change touches that case, the lead takes the case to the lane maintainer as a direction question before building; picking an answer silently gets an ESCALATE at the green light and a rebuild after the review loop.
* [A live test against another party's BYOT lab uses a dedicated sub-namespace whose controller key is generated on the test VM](decisions/a-live-byot-test-generates-its-controller-key-on-the-test-vm.md) - The test VM generates a fresh controller key for a sub-namespace kept for the run; only the public DID and the _awid TXT value leave it, the lab publishes the record, and the key is shredded with the VM. No key moves between hosts, and no outside party needs a route into the tester's host.
* [A test teardown that removes a fake CLI's directory waits on the process table, not on the fake's records](lessons/a-teardown-waits-on-the-process-table-not-the-fakes-records.md) - The Desktop backend exits on SIGTERM without signalling the CLI runs it launched, so a test that removes the directory a fake CLI writes into waits, after the server's exit, until no process runs from that directory; records the fake writes cannot see a run launched but not yet noted, and a full-path match misses a run under a non-ASCII parent.
* [A provider pin that adds a flag to an argv turns the kernel's exact-argv "never ran" checks vacuous](lessons/a-pin-that-adds-a-flag-turns-exact-argv-negatives-vacuous.md) - When a provider release adds a flag to a command the kernel's mirror-hook tests watch, update the positive checks to the release's exact new argv, and rewrite every negative "this never ran" check to match on the command and its operand prefix; an exact-string negative passes silently whatever ran. Run `npm ci` in a fresh tree before running even one such file.
* [A tested-aw bump rests on aw's own tag-to-tag diff, not on a relayed change list](lessons/a-tested-aw-bump-rests-on-the-tag-to-tag-diff.md) - Before oats.aweb records a new tested aw, read the aw source paths oats.aweb consumes across every tag from the old tested release to the new one, and write the release note from that; a change list relayed with the request is someone's selection and can miss what reaches oats.aweb.
* [The Desktop's CLI ceiling is a tested bound, with an allowlist above it](decisions/desktop-cli-ceiling-is-a-tested-bound-with-an-allowlist.md) - A Desktop accepts a released oats CLI of a later minor or major than its own and flags it aboveTested. Only an explicit allowlist (reads, terminals, Spawn, Start, Restart, colour, background) stays on; every other operation, future ones included, is refused at the backend's entry before any CLI runs, with one notice naming the Desktop to install.
* [Directory mode does its repository work in extra trees of its own, with the workspace briefing's --repo-always section](decisions/directory-mode-does-repository-work-in-its-own-extra-trees.md) - The directory briefing grants extra trees with the workspace briefing's "Extra trees" section byte for byte (`--repo` always), because a directory home's recorded repo is configuration context, not a Git tree; `./work` stays an owned directory that never becomes a repository.
* [Directory-mode briefing text is pinned outside the goldens, in the trigger fixture and the Desktop inspect fixtures](lessons/directory-briefing-text-is-pinned-outside-the-goldens.md) - No golden composes directory mode, so a change to injects/work-directory.md or the directory TASK.md line is caught by test/fixtures/trigger-pipeline-13 (re-record, then word-diff) and by six Desktop inspect fixtures (align by hand, run packages/desktop/test/inspect-fixture-briefings.test.mjs locally); both before the first push.
* [An older Desktop does worse against a newer kernel where it words the consequence itself](lessons/an-older-desktop-does-worse-where-it-words-the-consequence.md) - In the traced kernel minors, the N-1 Desktop did worse than show less or be refused in four cases, all where it writes the consequence sentence of a destructive action (Stop, Remove) or saves a whole definition (schedule edit). API integers and feature names never caught them, because each change kept the JSON shape and changed its meaning.
* [The owning human is the first Lineage fact of the instance panel, and a roster fact never waits on another read](decisions/owning-human-is-a-lineage-fact-in-the-instance-panel.md) - The Desktop shows the kernel's attributedHuman as "Owning human", the first row of the instance panel's Lineage section, only when it is set; instance names stay every label, and a fact the roster reports goes where the roster alone decides its visibility, never into a section an asynchronous read gates.
* [Re-approving goldens with a test-name filter deletes the goldens of every case it skipped](lessons/update-golden-with-a-name-filter-prunes-skipped-cases.md) - A full `UPDATE_GOLDEN=1` run of test/golden-fixtures.test.mjs deletes the whole golden tree before it writes, so with `--test-name-pattern` only the matched cases come back; scope the update with `UPDATE_GOLDEN_ARTIFACT`, which deletes nothing, or restore the rest from HEAD and re-verify before committing.
* [Workspace mode keeps member clones read-only and does its repository work in extra trees of its own](decisions/workspace-mode-edits-only-in-its-own-extra-trees.md) - The workspace briefing grants extra trees (`oats worktree add --repo <member>`, `--repo` always), so "read-all/edit-none" means edit none of the shared member clones; whether an instance changes code at all is its role's and task's call, not the mode's.
