* [The tested aw version is published by oats.aweb in its own data file, and onboarding pins aw to it only for a customer-run server](/nodes/oats-maintainer/decisions/tested-aw-is-published-by-oats-aweb-and-pinned-only-for-byot.md) - oats.aweb publishes the aw versions it was tested with as a public provider-owned data file ({min, tested}) that its floor module reads as the one source and that CI must run exactly; getting-started reads that file only at the catalog-pinned oats.aweb ref and installs aw@tested only on the customer-run (BYOT) branch, while hosted installs keep npm latest and record the installed version, narrowing, for that branch only, the integrations decision's rejection of pinning the install.

* [A workspace definition, a source library and a capability package are different responsibilities](/nodes/oats-maintainer/decisions/workspace-definition-is-not-a-package.md) - Shared team composition lives in a Git-backed workspace definition; behaviour lives in capabilities; a distribution package transports them; a local deployment realises them — different responsibilities that may share a repository, joined only by reciprocal membership; consuming is never joining.

* [Presentation features reuse one state contract unless divergence is justified](/nodes/oats-maintainer/stewardship/presentation-features-reuse-one-contract.md) - Review new instance-presentation features against the established state and mutation boundaries, requiring a reason for divergence so display choices do not acquire identity, policy or lifecycle meaning.

* [A provider release is tagged first, then mirrored and pinned in one re-proven framework PR](/nodes/integrations-expert/lessons/a-provider-release-is-mirrored-and-pinned-in-one-pr.md) - Tag first, then review the tag-identical mirror and every pin as one diff; the gate keeps the Desktop suite, with the suites in CI and only named affected test files run locally, and a pin is re-proven after another shared-file change lands.
* [Evaluate merge gates beyond code-seed catches](/nodes/oats-expert/lessons/evaluate-gates-beyond-code-seed-catches.md) - Compare a coordination gate's direction and evidence duties separately from code catches, and distinguish new human decisions from repeated requests for settled ones before treating request counts as necessary oversight.
* [Expertise lives in the soul and its node, so the lead weighs context and ownership against hand-off cost, not specialist against generalist](/nodes/oats-expert/lessons/expertise-lives-in-the-soul-so-weigh-context-and-ownership-against-hand-off-cost.md) - In two trials with the same model and the same knowledge content on every arm, generalist sessions won coding on checks and time while the expert arm won where ownership and standing context mattered, so the lead keeps a unit of work whole in one fresh session of the soul whose knowledge fits it, adds a hand-off only where ownership or context needs one, and keeps standing instances only for what must persist between events.
* [Send a hand-off as a message that wakes every waiter at an exact head; the forge is the record, never the signal](/nodes/oats-expert/lessons/send-a-hand-off-by-message-to-every-waiter-at-an-exact-head.md) - A plan, approval, verdict or merge written only on an issue or PR wakes nobody, and a merge mailed only to its author strands everyone else waiting on it, so the lead sends each hand-off as a message to every instance the plan says waits, naming the artefact at its exact head and the ask, and runs a check as a call to a fresh reviewer rather than a standing station.

* [Open a CI-only draft during kernel review convergence](/nodes/oats-kernel-expert/lessons/draft-pr-runs-ci-during-convergence.md) - When the kernel branch needs a PR to trigger CI, the expert opens a clearly non-review draft on the first push so exact-head CI runs during convergence rather than starting only after acceptance, and states green only from the completed run of the exact head, never from a watch that returned with zero checks.
* [A commit cherry-picked across a base change must be re-read as a diff against the new base](/nodes/oats-maintainer/lessons/a-cherry-pick-across-a-base-change-must-be-reread-as-a-diff-against-the-new-base.md) - When a developer rebuilds a branch on a newer base by cherry-picking, hunks written against the old base can reintroduce text the new base removed; the reviewer reads the full diff against the remote main, not only the lines the change was meant to touch.
* [A re-dated claim must be re-verified against the release it now names](/nodes/oats-maintainer/lessons/a-re-dated-claim-must-be-re-verified-against-the-release-it-now-names.md) - Verify version-qualified behavior against the named release; an unreleased-feature gate keeps its fallback without a guessed floor, and mirror-keyed checks prompt release-qualified wording when the feature ships.
* [A failed-job rerun does not pick up a later base fix](/nodes/oats-maintainer/lessons/a-rerun-does-not-pick-up-a-base-fix.md) - When PR CI failed on an old merge revision, rerunning that run does not test a fix subsequently merged to main; obtain fresh combination evidence and distinguish a branch update from an unchanged-head retrigger.
* [A transfer rehearsal must check what the forge returns and keeps per owner, not only that operations succeed through the old name](/nodes/oats-maintainer/lessons/a-transfer-rehearsal-must-check-what-the-forge-returns.md) - A rehearsal that proves every operation succeeds through a redirected old name misses tools that compare the new name the forge returns and state the forge keeps per owner, so before a move inventory what each consumer reads, including hand-kept host files and returned URLs, and change the consumers that will break before transferring.
* [Adoption evidence and authority must match the claimed outcome](/nodes/oats-maintainer/lessons/adoption-evidence-and-approved-scope.md) - Installation, usable execution, publication, delivery, consumption and learning are different evidence; an apparent gap is classified before anyone adds fields or authority; and review findings do not expand approved product scope.

* [Scoped release approval covers delivered behavior, including package pins](/nodes/oats-maintainer/lessons/scoped-release-approval-includes-package-pins.md) - Check an effort-scoped release approval against all behavior the candidate delivers, including package pins, rather than only its kernel diff.
* [Search the whole repository before declaring a cited file missing](/nodes/oats-maintainer/lessons/search-the-whole-repository-before-declaring-a-cited-file-missing.md) - A file cited by an older note that is absent from the directory you expected is not evidence that it was renamed or removed; a name search across the whole tree costs seconds and an invented history, once written into accepted knowledge, is a defect a reviewer has to catch.
* [Second-operator acceptance — what the gate is for, how to read its failures, and the contract-siblings rule](/nodes/oats-maintainer/lessons/second-operator-acceptance.md) - A published definition or operator guide is accepted only when an operator holding none of the authoring state reproduces it against the published combination and verifies by positive enumeration; its exit criterion is "every remaining item is named and owned", its failures fall into four owner-distinct classes, and its recurring finding — a contract adopted by one provider but not its siblings — is prevented by a same-release adoption rule.
* [A test harness must reproduce a known-good baseline before any delta it reports means anything](/nodes/oats-maintainer/lessons/validate-the-harness-against-a-known-good-baseline.md) - An isolated copy of a project can fail for environmental reasons that have nothing to do with the change under test, so run the unmodified control first and require it to match the trusted result.
* [Report an outcome only from a read-back of the target](/nodes/oats-maintainer/lessons/verify-the-remote-ref-after-every-scripted-push.md) - A chained push, merge or release script can fail mid-way while a later step still announces the intended outcome; a head, a merge or a tag is named to a reviewer only from a read-back of the remote or the forge, in its own step, guarded by what the read-back says.
* [Cross-workstream delivery: freeze the contract first, adopt then adapt, prove the merge](/nodes/oats-maintainer/stewardship/multi-workstream-delivery.md) - Freeze shared contracts before implementation, adopt then adapt sibling suites, and prove merge fidelity; ship-together sets need whole-set evidence before the first merge or an explicit release hold, and a paused shared-package contract stage is reverted before release.
* [Release judgement for the tag-driven lane](/nodes/oats-maintainer/stewardship/release-traps.md) - Release judgment distinguishes publication from artifact availability, rehearses released-state upgrades, changed macOS tests and newly taught skill commands before tags, runs the kernel tests that read a package's mirror before the package tag or plans their port, contains failed-tag repairs, separates one-off package patches from maintenance lines, gates package-soul adoption through catalog, explicit-tag and shared-workspace routes, holds new keys in shared member-repository souls until every reader accepts them, coordinates source, tag, mirror, every form of version pin and the framework release that carries them, pairs changes to shared instructional behaviour across separately released packages, treats a package rename as a republish whose old package is never uninstalled from a running host, cuts a template repository by an annotated template-v tag on its dated prep merge commit with its third-party notices, and plans tags around a hosted runner image's retirement brownouts.
* [How the OATS project ships and reviews](/nodes/oats-maintainer/stewardship/review-protocol.md) - Maintainer review binds verdicts to content and issue-recorded contract decisions, carries them only across an unchanged delta, preserves same-area integration evidence, requires timely and safely obtained verification, uses fresh readers and one second reader per PR, checks hand-written release claims, and judges tests against requirements rather than implementations.
