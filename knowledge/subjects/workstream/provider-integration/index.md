* [An idle waiter's checkpoint wake belongs to the waiter](/nodes/integrations-expert/decisions/checkpoint-wake-belongs-to-the-waiter.md) - A waiter-owned kernel job supplies an external checkpoint without depending on harness timers or messaging, but does not prove a child stalled or guarantee timely delivery.
* [Installers start from existing tools and preserve their ownership](/nodes/integrations-expert/decisions/installers-preserve-existing-tools-and-state.md) - An OATS installer reuses suitable existing tools, installs only missing ones, upgrades only its own installs, preserves user state for adoption, and filters bundled teaching from its runtime install path rather than merely documenting the composition leak.

* [Newer-than-tested warnings follow the service's release authority](/nodes/integrations-expert/decisions/newer-than-tested-warnings-follow-release-authority.md) - A provider's tested client bound is evidence rather than a refusal ceiling, and a managed-service exemption depends on that service owning server-before-client release order.
* [Official package repositories separate the distributed payload root from repository tooling, and every resource resolves inside that root](/nodes/integrations-expert/decisions/official-package-repositories-separate-the-payload-root-from-tooling.md) - A package repository keeps everything the kernel copies under one payload root that carries the distribution manifest, and everything else (schemas, scripts, tests, workflows, the package expert's soul) outside it; the integrity digest covers the payload only, a Git or catalog reference reads the payload root, and every manifest-named resource resolves beneath it or the integrity check is meaningless.
* [Teams in the messaging provider: the workspace's default team, explicit join and leave, one local identity per joined team](/nodes/integrations-expert/decisions/teams-in-the-messaging-provider-default-team-explicit-join.md) - Agreed 2026-09-25 on the human's priority: every instance lives in the workspace's default team; a soul's team labels only make wider teams eligible; joining is a spawn choice or one idempotent command at any time, leaving is the same command or automatic when eligibility disappears on live evidence; each joined team is a further local identity the provider records and revokes at retire; clarified 2026-11-03: a joined team that becomes the exact live default is not eligibility loss, and only respawn moves the primary identity.
* [The messaging integration's readiness reports the host wake daemon's version, read from the daemon's own status answer](/nodes/integrations-expert/decisions/the-messaging-integrations-readiness-reports-the-host-wake-daemons-version.md) - Because the host wake daemon is a long-running process whose version the PATH floor gate cannot see, readiness asks the daemon for its version through its status command and compares it with the client floor, reporting an outdated or stopped daemon as a problem and an unknown version as a warning; no process inspection. A missing wake is diagnosed from the daemon's own log, never from its status rows.

## Insight

### lesson

* [A client view that contradicts the source of truth is a client defect, not a missing fact — read the authoritative source, cite the message-level read, never rewrite a live identity](/nodes/integrations-expert/lessons/a-failing-readiness-diagnostic-is-not-a-missing-fact.md) - When a client's health check contradicts a command's own success receipt, or a listing disagrees with the single-message read, report the discrepancy and read the authoritative source (the registry route, the message envelope) before treating anything as missing; never rotate, re-publish or re-mint a live identity to satisfy a view that may itself be broken, and let only the receiver's verdict accept a signed send.
* [A fake CLI that accepts what the real binary refuses hides a broken hook — a provider that drives an external CLI is accepted on the whole lifecycle against the published binary](/nodes/integrations-expert/lessons/a-fake-cli-that-accepts-what-the-real-binary-refuses-hides-a-broken-hook.md) - Fakes model the released tool's refusals and outputs; acceptance needs the whole lifecycle on the published binary, one version floor, and explicit control of the binary and state the rehearsal actually exercises.
* [A fake CLI that hangs must start a child of its own](/nodes/integrations-expert/lessons/a-fake-that-hangs-must-have-a-child.md) - A single-process hang fake hides descendant leaks, so timeout and reader-termination tests must observe both the fake and its child on every external-CLI call path.
* [A fallback the contract defines is implemented in every path, readiness included, and is a warning, not a readiness problem](/nodes/integrations-expert/lessons/a-fallback-the-contract-defines-is-a-warning-not-a-readiness-problem.md) - When the contract says an input degrades to a defined default, every code path that consumes the value (each identity mode, spawn, readiness, remedies) takes that default and warns; readiness derives the value exactly as spawn does, and a provider that blocks on a defined fallback, or implements it in one mode only, turns the kernel's warning into an outage.
* [A global instance identity's address is released only by the authority that owns its lifecycle, so per-spawn global identities need that retire path settled first](/nodes/integrations-expert/lessons/a-global-instance-identity-leaves-a-permanent-address-behind.md) - On the messaging service a global identity can hold several team memberships and retire can revoke them all, but releasing its address is a separate lifecycle act with its own authority (a namespace controller key on a customer-controlled namespace; on the hosted service an owner's archive or the member's own deprovision with address deletion, under a human session or the member's own key), and enrolling an existing global identity into a further hosted team needs a human owner session; settle which of those a provider's retire and join can actually call before defaulting instances to global.
* [A grant is proven per path at the receiver — custody attachment is necessary, not sufficient, and scopes do not name the endpoints a path calls](/nodes/integrations-expert/lessons/a-grant-home-needs-a-custody-reference-for-encrypted-receive.md) - A session grant signs and decrypts only when its record carries the custody locator, so custody readiness is not grant readiness; and a grant holding every offered scope can still be refused on a path whose client makes a call no scope names; rehearse each operation per path and direction, read the receiver's verification, and trace a refusal to its request.
* [A hook reports only the cleanup it confirmed, and keeps the credential a retry needs](/nodes/integrations-expert/lessons/a-hook-reports-only-the-cleanup-it-confirmed.md) - Emit meta before failing, report only confirmed cleanup, re-check uncertain effects, retain credentials for key-dependent retries, and pair credential exclusion from retirement recovery with fail-closed hooks.
* [A lifecycle hook never trusts the ambient environment — hooks inherit the operator's process, and the operator can be another instance](/nodes/integrations-expert/lessons/a-lifecycle-hook-never-trusts-the-ambient-environment.md) - Spawn, launch and retire hooks run with the invoking process's environment; a hook that reads a locator, credential home or team from that environment can act for the wrong principal when the invoker is itself an instance, so every such input comes from the hook's own payload, its persisted meta or the instance home.
* [A live Pi TUI does not prove provider readiness](/nodes/integrations-expert/lessons/a-live-pi-tui-does-not-prove-provider-readiness.md) - Pi 1.3.0 could accept a prompt and remain silently running without a logged-in provider, so omitting a shared model pin avoids a portability assumption but does not establish an executable session.
* [A rehearsal's measurement must not change the state under test](/nodes/integrations-expert/lessons/a-measurement-must-not-change-the-state-under-test.md) - Establish that a diagnostic preserves the state being measured, and compare unexplained transitions with the observer's own actions before attributing them to the system under test.
* [Host-only settings are declared in the manifest and refused by the resolver, never enforced by the provider](/nodes/integrations-expert/lessons/a-merged-provider-payload-cannot-enforce-host-only-keys.md) - A setting that must come only from the host (a custody directory, a minting root) is declared hostOnly in the capability manifest so the resolver, which still sees the layers, refuses it from every committed file and spawn flag; the provider's hook receives one merged payload and is the wrong place to police provenance.
* [A document a provider writes for the kernel passes the kernel's own rule on the provider's stage; a reviewer reading a new key as a feature is how a strict wire breaks](/nodes/integrations-expert/lessons/a-provider-answer-is-validated-by-the-kernel-not-by-the-reviewer.md) - Check answers, hook outputs and manifests are kernel-consumed documents; the provider's stage vendors the kernel's validator or shape rule and runs every produced document through it, a new key is a wire question before it is a feature, and manifest keys follow the kernel's grammar (operations are keyed by bare name; the kernel adds the layer).
* [A provider that owns an in-life lifecycle owns its state file and its verbs — it never rewrites the kernel's instance record, and its skills never teach the native mutations underneath](/nodes/integrations-expert/lessons/a-provider-command-never-rewrites-the-kernels-instance-record.md) - Keep in-life state in a provider file mirrored through hook meta, never in instance.json, teach the provider's verbs, and use reported identity locations rather than derived paths or a silent default for an unavailable explicit task destination.
* [A provider release is tagged first, then mirrored and pinned in one re-proven framework PR](/nodes/integrations-expert/lessons/a-provider-release-is-mirrored-and-pinned-in-one-pr.md) - Tag first, then review the tag-identical mirror and every pin as one diff; the gate keeps the Desktop suite, with the suites in CI and only named affected test files run locally, and a pin is re-proven after another shared-file change lands.
* [A provider test that fakes the kernel's payload proves nothing about the kernel; a provider's meaning for a settings key is only as good as what the kernel puts there](/nodes/integrations-expert/lessons/a-provider-test-that-fakes-the-kernel-payload-proves-nothing-about-the-kernel.md) - When a provider gives a settings key a meaning the contract does not guarantee (settings.team as "the default team a host chose"), a test that hand-writes the payload without the key passes while the real kernel, which merges the primary label's team into that key, makes the provider do the opposite; check what the kernel actually merges before assigning meaning, and when the meaning is right, change the kernel's merge rather than guess from equality in the provider.
* [A team per workspace needs a service primitive](/nodes/integrations-expert/lessons/a-team-per-workspace-needs-a-service-primitive.md) - The messaging service has no idempotent create-or-return for a team, so a zero-step team per workspace cannot be improvised by the provider; the provider exposes setup as a guided step and never invents local shims, and the fix proposed here (a human CLI login in the provider's path) is superseded by team creation as the owner's account-level act outside OATS.
* [A delivery acknowledgement must name the stage its receipt proves](/nodes/integrations-expert/lessons/acknowledgement-stage-must-match-receipt.md) - A provider records a delivery mark only after the component that owns the agreed stage has acknowledged that stage; callback completion and whole-turn waits can prove the wrong thing.
* [Admit failed-run leftovers by type, not name](/nodes/integrations-expert/lessons/admit-leftovers-by-type-not-name.md) - Widening a provider's directory admission to accept failed-run leftovers requires expected-type checks before effects, exclusive creation of new outputs, and collision checks across the whole output set.
* [Live config validation belongs after confirmation, not in a reusable preview cache](/nodes/integrations-expert/lessons/config-validation-belongs-after-confirmation.md) - Validate an isolated baseline and candidate after confirmation and just before an atomic guarded write, because unchanged copied bytes do not prove an executable config's dependencies stayed unchanged.
* [Credential-free harness probes establish only the boundary they exercise](/nodes/integrations-expert/lessons/credential-free-harness-probes-have-bounded-proof.md) - A real TUI with a local stub provider can test input consumption without login, while real sandbox commands test particular permissions; neither substitutes for authenticated end-to-end acceptance.
* [Desktop persistence apply is a human handoff, not a classifier workaround](/nodes/integrations-expert/lessons/desktop-persistence-apply-is-a-human-handoff.md) - Agent-assisted desktop setup separates plan and check from the person's persistence-changing act, respects harness refusals, and limits each chosen option to its own effects.
