* [In a bb Claude thread a permission prompt becomes oats.core's claim, and a bb tell waits behind it](/claims/lessons/a-bb-permission-prompt-is-an-oats-claim-and-a-tell-waits-behind-it.md) - With the OATS env set for a bb Claude Code thread, a Bash permission interaction still fires Claude's own hooks, so oats.core records a permission claim in the home's events; but session inspect reads such a home as not launched, a spawn-only home lacks the PermissionRequest hook, and a bb tell sent meanwhile neither answers nor cancels the interaction but queues until it is resolved.
* [A bb plugin command's shortcut does not fire from a focused terminal; a capture-phase content script does](/claims/lessons/a-bb-plugin-shortcut-does-not-fire-from-a-focused-terminal.md) - In bb 0.50.1 a plugin command's default shortcut never fires while bb's terminal has the focus if the terminal can encode the chord. Only a trusted content script listening in the capture phase, or a chord the terminal cannot encode, reaches the plugin ahead of the program.
* [A bb plugin shows a terminal only from a plugin page or a thread header row, never from the sidebar or the overlay](/claims/lessons/a-bb-plugin-shows-a-terminal-only-from-a-plugin-page-or-a-thread-header-row.md) - In bb 0.50.1 a plugin opens bb's Terminal tab in two calls (create a terminal, then show it by id), and the second is accepted only from a plugin page (any terminal, no thread needed) or a thread header row (that thread's terminals); from the sidebar slot and the app overlay it answers false and leaves the command running unseen.
* [A bb plugin's openTab at mount is declined; retry until it is accepted](/claims/lessons/a-bb-plugins-opentab-at-mount-is-declined-retry-until-accepted.md) - In bb 0.50.1 `openTab` called once from a thread header row's mount effect returns false on every first load and thread switch, because the panel lists only bb's own tab at that moment. The same call 250 ms later is accepted, on desktop and at phone width.
* [A bb restart holds wake-broker mail cleanly but strands a wake already steered into a turn](/claims/lessons/a-bb-restart-holds-broker-mail-but-strands-a-steered-wake.md) - With the aw wake broker delivering into a bb thread through bb thread tell, mail sent while bb is down arrives exactly once after it returns, provided session inspect fails while bb is unreachable; but bb never resumes an interrupted turn, and a wake bb had already accepted as a steer leaves the thread in status error, acknowledged and without a turn, until a later tell restarts it.
* [A bb thread has no "stopped" status, so a session backend over bb records its own stop](/claims/lessons/a-bb-thread-has-no-stopped-status-so-a-session-backend-records-its-own-stop.md) - bb's thread statuses are pending, idle, starting, active, stopping and error; a settled stop reads idle and any tell restarts the thread, so a kernel that runs agents as bb threads must record its own stop and refuse input to a home it stopped, or a mail silently restarts a stopped agent.
* [When a home's captured setting blocks the refresh meant to reach it, read live only the fields the refresh changes, and pin the authority fields to the capture](/claims/lessons/a-captured-setting-that-blocks-its-refresh-reads-live-only-the-refreshed-fields.md) - A home captures its provider settings at spawn, so a later setup refresh (a newly mapped team, a new policy) never reaches an existing home's command, and a refusal whose fix is "rerun the refresh" is untrue there; read the live setting for the refreshed fields only, require every authority field (root, human, service, profile path and digest) to equal the captured one, and refuse with "respawn this home" otherwise.
* [A detail added to a contract on the provider side must widen every closed client decoder in the same step](/claims/lessons/a-contract-detail-must-widen-closed-client-decoders.md) - The Desktop's mail decoder refuses a whole answer with an unknown key, so the provider's "additive" field (identities().unreadableConversations) would have hidden all mail; a contract detail is additive only to a lenient reader.
* [A failing spawn hook hands its caller only its text, the code and whether the rollback was confirmed](/claims/lessons/a-failing-spawn-hook-hands-back-only-its-text-code-and-unconfirmed.md) - When a required spawn hook fails, the spawn's refusal carries the hook's warning text, E_REQUIRED_HOOK_FAILED (or E_HOOK_ENVIRONMENT_CONTRACT) and a hooks-only receipt with `unconfirmed: true` when the rollback could not confirm its effects; the hook's structured meta does not reach the answer. Evidence a design settles authority on must use what the kernel already projects, or name a new hook-output contract.
* [A service's member listing finds removal candidates; only a locally held signed copy authorises the removal](/claims/lessons/a-listing-finds-removal-candidates-a-local-signed-copy-authorises-the-removal.md) - A reconcile that removes leaked memberships must never take a certificate id or alias from an unsigned listing as authority; it acts only through the locally held signed copy (looked up by an id of the provider's own form, using the copy's own team and alias), a certificate a live home's record names is that home's whatever the listing says, and a row with no copy is listed, never removed.

* [A pi thread in bb's error state keeps its pi process, so a provider that reads error as a lost session strands the home](/claims/lessons/a-pi-thread-in-bb-error-keeps-its-process.md) - After a failed model turn bb marks a pi thread error while its long-lived pi process stays alive and a plain tell would recover it; a session provider that maps error to a missing session makes the kernel show the home lost, hide the failed-turn claim and refuse every input and resume, because a process of the last run still works in the home.
