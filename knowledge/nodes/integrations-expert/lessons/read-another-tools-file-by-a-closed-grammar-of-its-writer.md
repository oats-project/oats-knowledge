# The lesson

A messaging provider had to read one value, the service URL, from a YAML file its CLI writes.
The package has no YAML dependency, so the reader began as a regular expression and then as a
line search with continuation checks. Three fresh review rounds in a row each found a valid
YAML file it misread: a continuation line, a blank line before an indented continuation, and
the key inside a flow mapping or a multi-line quoted scalar. Each time the spawn would have
bound a server YAML doesn't give, and readiness said ready.

The fix was a closed grammar of what the CLI's writer emits:
- blank lines and comments;
- column-0 keys with a one-line scalar or an empty value;
- indented lines only under an empty-valued key.

The reader refuses anything else. On every accepted file it gives exactly the value YAML gives,
and a table of accepted and refused files pins that.

**Read as few values as the change needs.** Folding a second key into the same reader brought in
YAML 1.1's type resolution: `null`, `yes` and `0x10` are not strings. A URL can't resolve to any
of those, so a reader that returns only the URL avoids that whole class. Shape-check the lines
the change doesn't read, but don't parse their values. A later change that read a list
(`memberships[].team_id`) extended the same walker only as far as the writer's list of mappings.
It pinned the writer's exact output, generated by the writer's own serializer offline, as table
rows.

# How to apply

- Find the writer's output form at the version the package tests against: its serializer and
  call site, or a real run. Write the grammar from that form, never from "valid YAML".
- Decide what a file outside the grammar means for each check. Refuse where the value is
  required (no URL, no spawn). Make no decision where the check only predicts a refusal the tool
  makes anyway, and leave it to the tool: refusing a file the tool accepts is a new strictness.
- Return only the values the change consumes, and add a value only with its own table rows.
- Separate correctness from the security boundary. Anyone who can write the file can already
  name any server in it, so the reader is about correctness. The checks on the value itself
  (scheme, no userinfo, one argv element, never printed) are the boundary.

Rejected: vendoring a YAML parser, the package's first third-party code, a supply-chain
decision for one key; asking the tool, which had no offline read of that value; more
line-search fixes, which are unbounded and the review loop's warning sign. (These rejected
alternatives are source-reported: the PR record names the rounds and the grammar, not them.)

Relates to [integration guidance and local validation follow the real contract](/nodes/integrations-expert/lessons/guidance-names-only-verbs-the-target-cli-exposes.md),
which validates a service-defined value identically in every path. This lesson refines it for

# Evidence and limits

Evidence: OKF proposal from integrations-expert/aweb-container-followups-lead, 2026-11-13;
notes/read-a-tools-file-by-a-closed-grammar.md. Observed in awebai/oats-aweb#243 (closes #241,
review rounds 3 to 8) and #258 (closes #256, the memberships list). The URL reader was run
by the maintainer over the 64 real files of that CLI on one host, and it accepted all 64. It is
one provider and one CLI's YAML writer. The limit that the reader decides only those values and
is not a YAML validator is stated in that package's README.

Maintainer review of oats-knowledge#377: the commits of awebai/oats-aweb#243 record rounds 3
to 5 finding a value cut at its first line, a continuation after a blank line, and an
`aweb_url` that wasn't top-level (inside a flow mapping or a multi-line quoted scalar); the
closed grammar at round 5; the narrowing to `aweb_url` at round 6 because reading every value
brought in YAML's type resolution; and the limit written at round 7. The PR records round 8's
approval with a differential against PyYAML, and its review comments the 64-file run. #258
records the memberships list read through the same walker, with the writer's exact output
captured by running its serializer. The test results are source-reported, not rerun.
