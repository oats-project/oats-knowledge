# Stewardship

How the OATS project ships: judgement only, each concept with an owner and an
update-on-change rule; procedures live in the oats-expert soul's skills.

* [Direct knowledge proposals should retain doctrine and maintainer review](direct-knowledge-proposals-retain-maintainer-review.md) - Move toward working agents opening knowledge PRs themselves under unchanged promotion doctrine, but retain current harvest duties until the knowledge-package owner designs and ships the authority and independent-review transition.
* [Reassess coordination across use cases before adaptive onboarding](coordination-redesign-precedes-adaptive-onboarding.md) - Treat the current role model as a candidate rather than a design constraint, evaluate alternatives through research and real trials with human oversight central, and hold use-case-adaptive onboarding for the coordination outcome.
* [Presentation features reuse one state contract unless divergence is justified](presentation-features-reuse-one-contract.md) - Review new instance-presentation features against the established state and mutation boundaries, requiring a reason for divergence so display choices do not acquire identity, policy or lifecycle meaning.
* [Coordination policy lives in capabilities, not in the kernel or oats.core](coordination-policy-lives-in-capabilities.md) - Keep coordination policy in composed capabilities, deliver the redesign as tagged template repositories adapted into workspace-owned capabilities with a human guide (template-v tags that no package pin can resolve, the frozen package left for existing pins, the package-rename route rejected), and retain the existing cleanup and action-required lifecycle-message rules until explicitly changed.
* [How the OATS project ships and reviews](review-protocol.md) - Maintainer review binds verdicts to content and issue-recorded contract decisions, carries them only across an unchanged delta, preserves same-area integration evidence, requires timely and safely obtained verification, uses fresh readers and one second reader per PR, checks hand-written release claims, and judges tests against requirements rather than implementations.
* [One release lane does the final review, merge and tags; project lanes are defined by their own maintainers](release-lane-and-project-lanes.md) - One release lane owns final review, merge and tags; project maintainers define lanes without sign-off, route follow-ups by the map, review with one second reader, record changed practice and hand over approved heads, while the directing human's lanes launch routine filed work without asking again; child overflow preserves accountability and the onboarding redesign has bounded human-sign-off and reviewer-routing exceptions.
* [The onboarding redesign has one reviewer on Pepe's side, the release lane](onboarding-redesign-release-only-review.md) - For the onboarding redesign only, Juan's side decides the design and the release lane alone reviews for Pepe's side, returning changes that are too complicated, too slow or contrary to direction while preserving bilateral contract agreement before build.
* [Release judgement for the tag-driven lane](release-traps.md) - Release judgment distinguishes publication from artifact availability, rehearses released-state upgrades, changed macOS tests and newly taught skill commands before tags, runs the kernel tests that read a package's mirror before the package tag or plans their port, contains failed-tag repairs, separates one-off package patches from maintenance lines, gates package-soul adoption through catalog, explicit-tag and shared-workspace routes, holds new keys in shared member-repository souls until every reader accepts them, coordinates source, tag, mirror, every form of version pin and the framework release that carries them, pairs changes to shared instructional behaviour across separately released packages, treats a package rename as a republish whose old package is never uninstalled from a running host, cuts a template repository by an annotated template-v tag on its dated prep merge commit with its third-party notices, and plans tags around a hosted runner image's retirement brownouts.
* [Cross-workstream delivery: freeze the contract first, adopt then adapt, prove the merge](multi-workstream-delivery.md) - Freeze shared contracts before implementation, adopt then adapt sibling suites, and prove merge fidelity; ship-together sets need whole-set evidence before the first merge or an explicit release hold, and a paused shared-package contract stage is reverted before release.
